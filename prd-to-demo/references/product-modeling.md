# 产品建模与证据合同

## 四类证据

| 类别 | 定义 | 写法 |
| --- | --- | --- |
| PRD 明确 | 原始高优先级来源直接陈述 | 给出 Source ID、位置和忠实转述 |
| 基于 PRD 推导 | 为连接已知事实而作出的产品推理 | 写明推导依据、影响和待确认点 |
| Demo Mock | 仅为演示任务而构造的数据或行为 | 写明真实系统应由谁、何时提供 |
| 待产品确认 | 来源缺失、冲突或会改变范围的决策 | 写成可回答问题，并给出影响 |

不得把“常见做法”归为 PRD 明确。用户确认推导后，在决策记录中保留原类别和确认时间，不要删除推导历史。

## 建模顺序

1. **边界**：产品服务谁、解决什么、不解决什么、与哪些外部系统交互。
2. **角色**：职责、目标、数据范围、可执行动作和被禁止动作。
3. **对象**：唯一标识、关键字段、关系、Owner 和真实来源。
4. **状态机**：初始态、合法转换、触发者、后台动作、失败与回退。
5. **规则**：条件、结果、优先级、例外、阈值和冲突处理。
6. **权限**：查看、创建、编辑、提交、审批、发布、撤回、删除、配置和审计。
7. **证据**：把每条模型结论连接到来源和后续界面。

## 追踪 ID

使用稳定前缀：

- `REQ-###`：需求与业务规则。
- `ROLE-###`：角色与权限。
- `OBJ-###`：核心对象。
- `STATE-###`：状态或转换。
- `Q-###`：待确认问题。

不要用页面名称作为需求 ID，因为页面结构会调整而产品事实不应随之漂移。

## 状态机检查

对每个核心对象回答：

- 谁创建，创建前置条件是什么？
- 哪个动作改变状态？动作同步还是异步？
- 后台会执行哪些检查或任务？
- 失败、超时、重复提交和撤回如何处理？
- 谁能看见、处理或恢复？
- 历史记录是否保留？修改是否产生新版本？
- 终态能否再次进入流程？

若 PRD 没有答案，归入推导或待确认，不通过漂亮的 UI 隐藏缺口。

## 权限矩阵

至少覆盖：查看、创建、编辑、提交、审批、发布、撤回、删除、配置、审计。分别记录角色资格、资源范围、状态条件、自操作限制和替代入口。界面禁用与路由权限必须表达同一规则。

## 产品合同门禁材料

提交给用户确认：

1. 一句话目标与非目标。
2. 角色和核心任务。
3. 对象关系与生命周期。
4. 关键业务规则和后台动作。
5. 权限矩阵。
6. 来源冲突、推导、Mock 和待确认清单。
7. 变更影响范围。

没有明确确认时，不进入页面规划或研发。
