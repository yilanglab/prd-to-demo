# PRD 输入盘点

## 来源优先级

按以下顺序处理冲突，除非用户明确指定其他顺序：

1. 产品负责人提供的原始 PRD 与明确补充说明。
2. 同一来源中日期更新、版本更高且有变更记录的材料。
3. 经用户确认的产品合同与决策记录。
4. 已有 Agent 分析、会议纪要和接口说明。
5. 竞品、视觉参考与实现猜测。

低优先级来源不能静默覆盖高优先级来源。记录冲突双方、影响页面和待决策人。

## 盘点步骤

1. 枚举 `.docx`、`.pdf`、`.md`、`.mdx`、`.png`、`.jpg`、`.jpeg`、`.webp`、`.svg` 等来源。
2. 记录文件名、相对路径、格式、修改时间、大小和可读状态。
3. 标记原始 PRD、二级分析、视觉参考、技术约束和历史产物。
4. 检查目录中的 `package.json`、`components.json`、TypeScript、Tailwind、文档和 `components/ui`。
5. 不读取 `.git`、`node_modules`、构建输出和缓存作为产品来源。

使用 `scripts/inspect-project.mjs` 获得确定性目录报告。脚本只负责发现，不负责判断哪份文档为事实来源。

## 多格式读取

- DOCX：保留标题层级、表格、批注可见信息和图片位置；不要只抽取连续纯文本。
- PDF：检查页码、表格、流程图和扫描页；OCR 内容需标记识别不确定性。
- Markdown/MDX：保留链接、代码块、frontmatter 和相对资源引用。
- 图片：记录图中文字、布局关系和无法确认的视觉含义；截图不是完整业务合同。
- 混合来源：使用统一追踪 ID 连接同一需求，不按文件各建一套互相脱节的模型。

## 条件式工具路由

- DOCX：使用当前环境的文档读取能力，保留标题层级、表格、批注和嵌图位置；纯文本抽取只能用于检索，不能作为完整读取证据。
- PDF：使用当前环境的 PDF 读取与页面渲染能力，保留页码、表格、流程图与页面布局证据；对扫描页标记 OCR 置信度和无法确认内容。
- 图片、截图与流程图：使用当前环境的图像查看能力，记录图中文字、空间关系、连线和视觉层级；不要从单张截图推断完整业务规则。
- Markdown/MDX：按文本结构读取，并保留 frontmatter、链接、代码块和相对资源。若文件混有图表或嵌入资源，按对应格式补充读取。

若环境缺少相应能力，记录受影响的页码、表格或图像，标为部分可读或待产品确认；不得把纯文本抽取写成完整读取。

## 来源登记字段

| 字段 | 要求 |
| --- | --- |
| Source ID | 稳定标识，如 `SRC-001` |
| 类型 | 原始 PRD / 补充说明 / 二级分析 / 视觉参考 / 技术约束 |
| 版本与日期 | 原文可得则填写，不可得则明确未知 |
| 作者或责任人 | 不推测匿名材料作者 |
| 范围 | 该来源覆盖的功能或页面 |
| 可读性 | 完整 / 部分可读 / 不可读 |
| 优先级 | 用于冲突判断 |

## 停止条件

- 原始 PRD 不可访问，且任务要求严格依据其内容。
- 关键表格或流程图无法读取，继续会改变核心生命周期或权限。
- 多份高优先级来源直接冲突，且没有用户决策。
- 目标目录包含无法区分归属的未提交修改，继续初始化可能覆盖用户资产。

满足停止条件时，只报告已知事实、受影响范围和所需输入，不用猜测填补。
